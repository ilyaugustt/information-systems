## 1. Цели и предпосылки

### 1.1 Зачем идём в разработку продукта?

Социальная сеть ежедневно получает до **500 000 комментариев**. Текущий процесс модерации — ручной или отсутствующий полностью. Это создаёт три критические проблемы:

- **Регуляторный риск:** РКН ведёт мониторинг качества модерации; пропуск запрещённого контента грозит штрафами и блокировкой платформы.
- **Операционная неэффективность:** команда модераторов физически не справляется с объёмом; ручная выборка охватывает < 1% потока.
- **Упущенный бизнес-инсайт:** данные о тональности аудитории не используются для улучшения контент-стратегии и рекламных кампаний.

### 1.2 Почему ML сделает лучше, чем сейчас?

| Критерий | Текущий процесс | ML-система |
|---|---|---|
| Покрытие | < 1% комментариев | 100% в реальном времени |
| Скорость решения | часы / дни | < 500 мс |
| Субъективность | высокая (зависит от модератора) | стандартизированная шкала |
| Масштабируемость | линейно зависит от найма | горизонтальное масштабирование |
| Аналитика | отсутствует | дашборды, тренды, алерты |

### 1.3 Бизнес-требования и ограничения

**Требования:**
- Precision по классу «запрещённый контент» ≥ 0.95 (недопустимо ложно пропускать нарушения).
- Задержка обработки одного комментария ≤ 500 мс (p99).
- Доступность системы ≥ 99.9% (не более 8.7 часов простоя в год).
- Хранение логов решений не менее 3 лет (требование регулятора).

**Ограничения:**
- Персональные данные пользователей не должны покидать российский контур (ФЗ-152, локализация данных).
- Нельзя использовать зарубежные облачные платформы для хранения контента.
- Бюджет MVP — ограничен; приоритет инфраструктуры на bare-metal или отечественном облаке (Yandex Cloud / VK Cloud).

### 1.4 Функциональные и нефункциональные требования

**Функциональные:**
- Классификация комментария по трём классам: `позитивный`, `нейтральный`, `негативный`.
- Отдельная бинарная метка `нарушение` (запрещённый контент по 149-ФЗ).
- API для внешнего обращения (модераторский интерфейс, рекламный кабинет).
- Возможность ручного переопределения решения модератором с сохранением в обучающую выборку (Human-in-the-loop).
- Алерты при резком росте доли негативных / нарушающих комментариев.

**Нефункциональные:**
- RPS: пиковая нагрузка до **10 000 req/s** (500k комментариев / 50 секунд «пиковой минуты»).
- Latency: p50 ≤ 100 мс, p99 ≤ 500 мс.
- Масштабируемость: горизонтальная, без переписывания кода.
- Audit trail: каждое решение логируется с меткой времени, ID модели, версией и уверенностью.

### 1.5 Процесс пилота и критерии успеха

**Критерии успеха пилота:**
- Precision (нарушения) ≥ 0.95 на hold-out выборке.
- Recall (нарушения) ≥ 0.80 (пропустить не более 20% реальных нарушений).
- Снижение нагрузки на команду модераторов на ≥ 60%.
- Нулевые штрафы РКН за период пилота.

**Процесс:**
1. **Недели 1–2:** сбор и разметка исторических данных (минимум 50 000 комментариев с ручными метками).
2. **Недели 3–4:** обучение baseline-модели (RuBERT fine-tune).
3. **Недели 5–6:** A/B: 20% трафика через ML, 80% — ручная проверка параллельно; сравнение качества.
4. **Неделя 7:** анализ результатов, решение о переходе к MVP.

### 1.6 MVP vs технический долг

**MVP (итерация 1):**
- Классификация тональности (3 класса) + флаг нарушения.
- REST API для интеграции с модераторским интерфейсом.
- Базовый дашборд: доля классов по времени.
- Human-in-the-loop: форма обратной связи модератора.
- Очередь Kafka для асинхронной обработки.

**Технический долг (следующие итерации):**
- Многоязычная поддержка (комментарии на других языках).
- Детекция специфических типов нарушений (экстремизм, CSAM, дезинформация — отдельные модели).
- Персонализированные алерты для рекламодателей.
- Объяснимость (SHAP/LIME — почему именно так классифицировано).
- Автоматическое переобучение по накопленной разметке модераторов.

## 2. Методология

### 2.1 Техническая постановка задачи

**Основная задача:** мультиклассовая текстовая классификация (positive / neutral / negative) + бинарная классификация (violation / ok).

Используются два отдельных выхода:
- **Sentiment head** — softmax, 3 класса.
- **Violation head** — sigmoid, бинарный.

Оба head-а обучаются поверх одного общего энкодера (multi-task learning), что снижает затраты на инференс.

**Архитектура модели:**

```
[CommentText] → Tokenizer → RuBERT-base (frozen ×8 layers) → [CLS] embedding
                                                              ↓
                                              Shared Dropout (p=0.3)
                                             /                        \
                             Linear(768→3) + Softmax        Linear(768→1) + Sigmoid
                                    ↓                                 ↓
                              Sentiment label                   Violation flag
```

**Обоснование выбора RuBERT:**
- Pre-trained на русскоязычном корпусе (Wikipedia RU + news).
- Хорошо переносит слэнг и эмодзи при fine-tuning.
- Размер модели ~550 MB — разумный баланс качества и скорости.
- Альтернатива — ruRoBERTa-large (лучше качество, но вдвое медленнее) — оставляем как апгрейд.

### 2.2 Необходимые данные

| Источник | Описание | Обязательность |
|---|---|---|
| Исторические комментарии | Не менее 50k с ручной разметкой тональности | **Критично** |
| Реестры запрещённого контента РКН | Словари, паттерны, ссылки | **Критично** |
| Обратная связь модераторов | Переопределения решений ML | Важно (для переобучения) |
| Метаданные поста | Тематика, тип контента | Желательно |
| Профиль автора | История нарушений, возраст аккаунта | Желательно (для рискового скоринга) |

**Без чего нельзя решить задачу:**
- Размеченный датасет на русскоязычных комментариях с примерами реальных нарушений (минимум 5 000 позитивных примеров нарушений).
- Список актуальных стоп-слов и паттернов по требованиям РКН.

### 2.3 Метрики качества

| Метрика ML | Формула | Связь с бизнес-результатом |
|---|---|---|
| **Precision (violation)** | TP / (TP + FP) | Ложные блокировки → жалобы пользователей, потеря вовлечённости |
| **Recall (violation)** | TP / (TP + FN) | Пропущенные нарушения → штрафы РКН |
| **F1 (violation)** | Гармоническое среднее P и R | Общий баланс |
| **Macro-F1 (sentiment)** | Среднее F1 по 3 классам | Качество аналитики тональности |
| **Latency p99** | 99-й процентиль задержки | SLA платформы |
| **Throughput** | Комментариев/сек | Способность обслуживать пик |

**Порог принятия решения (violation):** настраивается оператором. По умолчанию 0.7 — выше: автоблокировка; 0.5–0.7: отправка на ручную проверку; ниже 0.5: автоодобрение.

### 2.4 Риски на этапе анализа и моделирования

| Риск | Вероятность | Действие |
|---|---|---|
| Дисбаланс классов (нарушений < 1%) | Высокая | Oversampling (SMOTE), взвешенный loss |
| Дрейф данных (новый сленг, эвфемизмы) | Высокая | Мониторинг PSI, переобучение раз в 2 недели |
| Низкое качество разметки | Средняя | Crowdsourcing + inter-annotator agreement (κ ≥ 0.7) |
| Adversarial-тексты (намеренное искажение) | Средняя | Аугментация с опечатками, символьными заменами |
| Предвзятость модели (demographic bias) | Низкая | Аудит на срезах по регионам, темам |

## 3. Подготовка пилота

### 3.1 Способ оценки пилота

**Shadow mode**: система работает параллельно с ручной модерацией, не влияя на реальные блокировки. Сравниваются решения ML и решения модераторов на одних и тех же комментариях.

**Метрики оценки пилота:**
- Confusion matrix на 10 000 комментариев, размеченных вручную.
- Cohen's kappa между ML и разными модераторами.
- Время, сэкономленное модераторами (часы/день).
- Количество «ложных тревог» (FP) за неделю.

### 3.2 Критерии успешного пилота

1. Precision (violation) ≥ 0.95 на тестовой выборке.
2. Recall (violation) ≥ 0.80.
3. Задержка инференса p99 ≤ 500 мс при нагрузке 200 RPS (масштаб пилота).
4. Модераторы оценивают качество ≥ 4/5 (опрос по итогам).
5. Ноль инцидентов с регулятором за период пилота.

### 3.3 Подготовка пилота

**Шаг 1 — Данные (2 недели):**
- Экспорт 200 000 исторических комментариев (последние 3 месяца).
- Разметка 50 000 через краудсорсинг (Яндекс.Толока).
- Формирование train/val/test: 70% / 15% / 15%.
- Проверка дисбаланса; применение oversampling при соотношении нарушений < 2%.

**Шаг 2 — Модель (2 недели):**
- Fine-tuning RuBERT-base на train-выборке.
- Подбор порога decision threshold на val-выборке (grid search по F1-violation).
- Оценка на hold-out тесте.

**Шаг 3 — Инфраструктура пилота (1 неделя):**
- Развёртывание модели в Docker-контейнере (2 GPU-реплики).
- Подключение к теневому потоку комментариев через Kafka topic `comments.shadow`.
- Интеграция с модераторским интерфейсом (read-only: только просмотр предсказаний).

**Шаг 4 — Запуск и мониторинг (4 недели):**
- Параллельная работа ML + ручная модерация.
- Еженедельные отчёты по метрикам.
- Сбор обратной связи модераторов.

## 4. Внедрение для production-системы

### 4.1 Архитектура решения

> Подробная диаграмма: [diagrams/architecture.md](diagrams/architecture.md)

**Компоненты:**

| Компонент | Технология | Назначение |
|---|---|---|
| API Gateway | Nginx + Kong | Балансировка, rate limiting, аутентификация |
| Comment Ingestion | Apache Kafka | Приём потока комментариев, буферизация |
| ML Inference Service | FastAPI + TorchServe | Инференс модели, возврат предсказания |
| Model Registry | MLflow | Версионирование моделей, A/B деплой |
| Feature Store | Redis (hot) + PostgreSQL (cold) | Быстрый доступ к фичам пользователя и поста |
| Decision Engine | Python service | Применение бизнес-правил поверх предсказаний |
| Action Service | gRPC | Блокировка/пометка комментария в БД соцсети |
| Monitoring | Prometheus + Grafana + Evidently AI | Метрики latency, quality drift, data drift |
| Audit Log | ClickHouse | Хранение всех решений (3 года) |
| Human-in-the-Loop | Web UI | Интерфейс модератора для переопределений |

**Поток данных (happy path):**
```
User posts comment
      ↓
API Gateway → Kafka topic: comments.raw
      ↓
ML Inference Service (async consume)
  → Tokenize → Model forward → [sentiment, violation_score]
      ↓
Decision Engine
  → if violation_score > 0.7: auto-block
  → if 0.5–0.7:  queue for human review
  → else: approve
      ↓
Action Service → Update comment status in main DB
      ↓
Audit Log → ClickHouse (async write)
```

### 4.2 Инфраструктура и масштабируемость

**Выбранная инфраструктура:** Yandex Cloud (соответствие ФЗ-152, российский контур).

| Компонент | Конфигурация | Обоснование |
|---|---|---|
| ML Inference | GPU-кластер: 4× V100 (16 GB), autoscaling | Инференс BERT требует GPU для latency SLA |
| Kafka | 3-нодный кластер, репликация 3× | Надёжность, пиковая нагрузка 10k msg/s |
| Redis | 3-нодный cluster (32 GB RAM) | Кэш фич с TTL; snappy-сжатие |
| PostgreSQL | Primary + 2 read replicas | ACID-транзакции для audit и разметки |
| ClickHouse | 2-шардный кластер | Аналитические запросы по 500M+ записям |

**Масштабируемость:**
- ML Inference — горизонтальное масштабирование (k8s HPA по CPU/GPU utilization).
- Kafka partitions = 32 (достаточно до 50k msg/s без пересоздания топика).
- Stateless сервисы (Inference, Decision Engine) — добавление реплик без даунтайма.

**Плюсы архитектуры:**
- Полная развязка через Kafka: спайк нагрузки не роняет систему.
- Human-in-the-loop встроен в поток: переопределения автоматически попадают в обучающую выборку.
- Распределённое хранение: горячие данные в Redis (< 1 мс), аналитика в ClickHouse (не нагружают OLTP).

**Минусы / ограничения:**
- Зависимость от Yandex Cloud — vendor lock.
- GPU дорого при постоянной нагрузке; при низком трафике — переплата.
- Kafka увеличивает end-to-end latency на ~50–100 мс (приемлемо для асинхронной модерации).

### 4.3 Требования к работе системы (SLA)

| Параметр | Цель |
|---|---|
| Availability | 99.9% (≤ 8.7 ч/год) |
| Throughput | 10 000 комментариев/сек (пик) |
| Latency (p50) | ≤ 100 мс |
| Latency (p99) | ≤ 500 мс |
| Model refresh | ≤ 2 недели (автоматическое переобучение) |
| Audit log retention | 3 года |
| RTO (Recovery Time Objective) | ≤ 15 мин |
| RPO (Recovery Point Objective) | ≤ 5 мин |

### 4.4 Риски и неопределённости

| Риск | Оценка | Митигация |
|---|---|---|
| Изменение требований РКН | Высокий | Конфигурируемые правила в Decision Engine без деплоя модели |
| Дрейф модели (новый сленг, обход фильтров) | Высокий | Еженедельный мониторинг PSI + автоматический алерт на ретрейн |
| GPU-дефицит / рост стоимости | Средний | Квантизация модели (INT8) для снижения GPU-требований на 60% |
| Утечка PII через audit log | Средний | Маскирование имени/ID пользователя в логах; шифрование at-rest |
| Ложноположительные блокировки (PR-риск) | Средний | Высокий порог авто-блокировки (0.7) + прозрачный апелляционный процесс |
| Зависимость от разметчиков | Низкий | Active learning: модель сама выбирает «сложные» примеры для разметки |
